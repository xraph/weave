---
title: Multi-Tenancy
description: How Weave scopes collections, documents and chunks to tenant and app contexts, and where it doesn't.
---

Weave records a tenant on every collection, document and chunk, and filters retrieval by it. It does not filter everything by it. Reads and deletes by ID, and list calls without a tenant filter, see every tenant's data. This page says exactly which calls are scoped so you know where your own checks go.

## Setting the scope

```go
import "github.com/xraph/weave"

ctx = weave.WithTenant(ctx, "tenant-1")
ctx = weave.WithApp(ctx, "myapp")
```

Both are plain strings on the context. Neither is required: with no tenant, everything is written with an empty `TenantID` and retrieval searches across all tenants.

## What the tenant does

| Call | Uses the context tenant |
|------|-------------------------|
| `CreateCollection` | Sets `TenantID` (and `AppID` from `WithApp`) when the collection leaves them empty |
| `GetCollectionByName` | Looks the name up within the tenant |
| `Ingest`, `IngestBatch` | Stamps the tenant on the document, its chunks and the `tenant_id` key of each vector |
| `Retrieve`, `HybridSearch` | Filters the vector search to `tenant_id` |
| `GetCollection`, `GetDocument`, `GetChunk` | No, any ID is returned |
| `DeleteCollection`, `DeleteDocument` | No, any ID is deleted |
| `CollectionStats`, `ReindexCollection` | No |
| `ListCollections`, `ListDocuments`, `ListChunks`, `Count*` | Only through the filter's `Tenant` field, see below |

`Ingest` doesn't check that the target collection belongs to the context tenant. A caller with another tenant's collection ID can write into it (the new document gets the caller's tenant).

`AppID` is recorded on collections and nothing else. No call filters by it.

## Scoping reads yourself

List calls take an explicit tenant. `Tenant: nil` means every tenant, and a pointer means an exact match:

```go
tenant := weave.TenantFromContext(ctx)

cols, err := eng.ListCollections(ctx, &collection.ListFilter{Tenant: &tenant})
docs, err := eng.ListDocuments(ctx, &document.ListFilter{
    CollectionID: colID,
    Tenant:       &tenant,
})
```

For a lookup by ID, compare the owner after you load it:

```go
col, err := eng.GetCollection(ctx, colID)
if err != nil {
    return err
}
if col.TenantID != weave.TenantFromContext(ctx) {
    return weave.ErrCollectionNotFound
}
```

The HTTP routes don't do either of these, so in a multi-tenant deployment put an authorization check in front of the list, get, delete, stats and reindex routes.

## Retrieval

At ingest, each vector's metadata gets `tenant_id` and `collection_id`. `Retrieve` adds both to the search filter:

| You pass | Tenant filter |
|----------|---------------|
| nothing, with a tenant on the context | the context tenant |
| `engine.WithTenantID("t")` | `t`, overriding the context |
| `engine.WithTenantFilter("t")` | exactly `t`, overriding the context |
| `engine.WithTenantFilter("")` | rows with no tenant |
| nothing, no tenant on the context | none, every tenant |

The in-memory and pgvector stores apply it as an exact match on the `tenant_id` metadata key. The Fabriq store also sets Fabriq's own tenant scope from it.

## Tenant and app

| Field | Recorded on | Filtered by |
|-------|-------------|-------------|
| `TenantID` | collections, documents, chunks, vectors | retrieval, `GetCollectionByName`, and list filters you set |
| `AppID` | collections | nothing |

Collection names are unique per tenant, so two tenants can each have a `support-docs` collection.

## Background jobs

A job that isn't serving a request should build its own context, so the request's cancellation doesn't stop it and the tenant is the one you meant:

```go
func reindex(eng *engine.Engine, tenantID string, colID id.CollectionID) error {
    ctx := weave.WithTenant(context.Background(), tenantID)
    return eng.ReindexCollection(ctx, colID)
}
```

`ReindexCollection` doesn't read the tenant; each vector it rewrites keeps its chunk's stored tenant.
