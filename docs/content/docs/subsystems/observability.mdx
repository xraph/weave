In a Forge app you don't set anything up. The extension hands the engine your app's metrics and logger, and forge installs the tracer provider, so an ingest or a retrieval shows up as spans under the request's server span and as series on `/_/metrics`. Grove's `db.client` spans for the store calls nest under Weave's spans.

Outside Forge, spans go to whatever global tracer provider you install with `otel.SetTracerProvider`. Metrics need a go-utils metrics sink:

```go
import gometrics "github.com/xraph/go-utils/metrics"

eng, err := engine.New(
    engine.WithStore(st),
    engine.WithVectorStore(vs),
    engine.WithEmbedder(emb),
    engine.WithChunker(chunker.NewRecursiveChunker()),
    engine.WithMetrics(sink), // any gometrics.Metrics; nil records nothing
)
```

Without `WithMetrics` the engine records no metrics. That's the default. Weave never records on `otel.Meter()`, because a Forge app installs no global MeterProvider and nothing recorded there would be exported.

## Spans

Every span below comes from the tracer `github.com/xraph/weave` and is `Internal` unless it says otherwise.

| Span | Parent | Attributes |
|------|--------|------------|
| `ingest document` | the caller's span | `weave.collection.id`, `weave.document.id`, `weave.chunker.kind`, `weave.vectorstore.kind`, `weave.content.bytes`, `weave.chunk.count` (once the content is chunked, so a later failure keeps it), `weave.result` |
| `chunk document` | `ingest document` | `weave.chunker.kind`, `weave.chunk.count` |
| `embed texts` | `ingest document`, `retrieve chunks`, `reindex collection` or the caller's span | `gen_ai.operation.name` (`embeddings`), `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `weave.embed.operation`, `weave.embed.inputs` |
| `upsert vectors` | `ingest document` or `reindex collection` | `weave.vectorstore.kind`, `weave.vector.count` |
| `retrieve chunks` | the caller's span | `weave.retriever.kind`, `weave.retrieve.top_k`, `weave.collection.id` (when set), `weave.retrieve.results`, `weave.retrieve.hydrated`, `weave.retrieve.orphaned`, `weave.result` |
| `search vectors` | `retrieve chunks` or the caller's span | `weave.vectorstore.kind`, `weave.search.top_k`, `weave.search.results` |
| `reindex collection` | the caller's span | `weave.collection.id`, `weave.vectorstore.kind`, `weave.reindex.documents`, `weave.reindex.chunks` |
| `POST` (Client) | `embed texts` | `http.request.method`, `server.address`, `server.port`, `http.response.status_code` |

`embed texts` and `search vectors` sit straight under the caller's span when `RetrieveCompare` makes them (the dashboard's retrieval page). `gen_ai.request.model` is the `model` param an embedder reports through `weave.Describer`, so an embedder that doesn't describe itself has no model on its span. `gen_ai.usage.input_tokens` doesn't depend on that: it's the sum of the `TokenCount` values the embedder returns, set whenever that sum is above zero. The OpenAI embedder sets both.

`retrieve chunks` reads each hit back with one `GetChunk`. You'll see those as grove spans, and the totals as `weave.retrieve.hydrated` and `weave.retrieve.orphaned`. An orphan is a hit whose chunk row is gone from the metadata store.

When you configure a retriever, it embeds the query and searches with its own embedder and vector store. Those calls happen inside `retrieve chunks` but get no `embed texts` or `search vectors` span of their own, and they don't count towards the GenAI metrics. The OpenAI embedder's `POST` span still shows the provider call.

`POST` is the OpenAI embedder's call to `{baseURL}/v1/embeddings`. It records the host and port of the base URL (any userinfo dropped) and the status, never the path, the query, the key or the texts. It starts on a context without baggage, because the provider is a third party and baggage from your clients can carry user or tenant IDs. The W3C `traceparent` header still goes. If you pass `WithOpenAIClient` a client whose transport is already traced, you'll get the call twice.

A failed span has status `Error`, an `error.type` attribute and an `exception` event that holds only `exception.type`. The type is the Weave sentinel the error wraps (`weave.ErrChunkNotFound`), the context error, or the Go type of the innermost error in the chain. Wrappers unwrap, so a transport failure under a `*url.Error` shows as what's inside it: `syscall.Errno` for a refused connection, `*net.DNSError` for a failed lookup, `*net.OpError` when nothing further unwraps. For a non-200 answer from the OpenAI endpoint, the `POST` span's `error.type` is the status code and the returned error is `*embedder.StatusError`. An ingest into a collection that doesn't exist is the caller's mistake, so it ends with `weave.result=not_found` and no error status.

No span carries query text, document or chunk content, titles, sources, metadata, tenant IDs, keys or an error's text.

## Metrics

Forge exports a metric name outside its semconv namespaces with a `forge_` prefix and no unit suffix, and turns dots in label names into underscores. The table uses the names you'll see on `/_/metrics`.

| Scraped name | Type | Labels |
|--------------|------|--------|
| `forge_weave_ingest_duration_seconds` | histogram | `chunker`, `result` |
| `forge_weave_retrieve_duration_seconds` | histogram | `retriever`, `result` |
| `forge_weave_vector_operation_duration_seconds` | histogram | `vectorstore`, `operation`, `result` |
| `forge_weave_retrieve_hits_orphaned_total` | counter | none |
| `forge_gen_ai_client_operation_duration` | histogram, seconds | `gen_ai_operation_name`, `gen_ai_provider_name`, `weave_embed_operation`, `error_type` |
| `forge_gen_ai_client_token_usage` | histogram, tokens | `gen_ai_operation_name`, `gen_ai_provider_name`, `weave_embed_operation`, `gen_ai_token_type` |

Every label value comes from a bounded set. All but `error_type` are fixed lists:

| Label | Values |
|-------|--------|
| `chunker` | `fixed`, `recursive`, `semantic`, `sliding`, `code`, `custom` |
| `retriever` | `similarity`, `mmr`, `hybrid`, `rerank`, `custom`, `none` (no retriever, a plain vector search) |
| `vectorstore` | `memory`, `pgvector`, `fabriq`, `custom` |
| `operation` | `search`, `upsert` |
| `result` | `ok`, `error`, and `not_found` on ingest when the collection doesn't exist |
| `gen_ai_operation_name` | `embeddings` |
| `gen_ai_provider_name` | `openai`, `local`, `custom` |
| `weave_embed_operation` | `ingest`, `query`, `reindex` |
| `error_type` | empty on success, otherwise the error type described above. It isn't a fixed list, but it is bounded: the values are the Weave sentinels, the two context errors and the Go error types your process can return, never error text |
| `gen_ai_token_type` | `input` |

A component's label is the `Kind` it reports through `weave.Describer`. A kind Weave doesn't ship, or a component that doesn't describe itself, is `custom`, so the strategy string on a request never becomes a label. The model is never a label either: it goes on the span only.

The two `gen_ai` metrics are the OpenTelemetry GenAI client metrics, with the buckets the GenAI conventions advise. `gen_ai` isn't one of forge's semconv namespaces, so they keep the `forge_` prefix and don't get a `_seconds` suffix. Nexus records the same two names with different keys: nexus carries `gen_ai_request_model` where Weave carries `weave_embed_operation`. If one app runs both, the families share a name and forge fills a missing label with an empty value, so nexus's rows have `weave_embed_operation=""` and Weave's have `gen_ai_request_model=""`. `sum by (gen_ai_provider_name)` still works across both, and `weave_embed_operation!=""` picks out Weave's rows.

Mind one double count. If you point Weave's OpenAI embedder at a nexus gateway in the same app (its base URL set to nexus), both sides record the call: Weave as `embeddings` with provider `openai`, and nexus as `embeddings` with whatever provider it routed to, often `openai` too. A sum over the whole family then counts that call twice, so filter on `weave_embed_operation` one way or the other.

The vector histogram only times calls the engine makes itself. For pgvector, grove also records `db_client_operation_duration_seconds` for the same queries.

Some PromQL to start from:

```text
# p95 ingest latency by chunker
histogram_quantile(0.95, sum by (le, chunker) (rate(forge_weave_ingest_duration_seconds_bucket[5m])))

# embedding tokens per second, by what they were for
sum by (weave_embed_operation) (rate(forge_gen_ai_client_token_usage_sum[5m]))

# failed embedding calls
sum by (error_type) (rate(forge_gen_ai_client_operation_duration_count{error_type!=""}[5m]))
```

## Metrics extension

The `observability` package also ships a `MetricsExtension`: a lifecycle extension that bumps a counter on each engine event. It's separate from the metrics above and you add it yourself.

```go
import "github.com/xraph/weave/observability"

metricsExt := observability.NewMetricsExtension()

eng, err := engine.New(
    engine.WithStore(st),
    engine.WithVectorStore(vs),
    engine.WithEmbedder(emb),
    engine.WithChunker(chunker.NewRecursiveChunker()),
    engine.WithExtension(metricsExt),
)
```

It doesn't count `IngestChunked`, `IngestEmbedded` or `Shutdown`, and it records no durations. Its counters have no labels:

| Metric | Scraped name | Event |
|--------|--------------|-------|
| `weave.collection.created` | `forge_weave_collection_created` | `OnCollectionCreated` |
| `weave.collection.deleted` | `forge_weave_collection_deleted` | `OnCollectionDeleted` |
| `weave.ingest.started` | `forge_weave_ingest_started` | `OnIngestStarted` |
| `weave.ingest.completed` | `forge_weave_ingest_completed` | `OnIngestCompleted` |
| `weave.ingest.failed` | `forge_weave_ingest_failed` | `OnIngestFailed` |
| `weave.documents.ingested` | `forge_weave_documents_ingested` | Documents ingested per `OnIngestCompleted` |
| `weave.chunks.created` | `forge_weave_chunks_created` | Chunks created per `OnIngestCompleted` |
| `weave.retrieval.started` | `forge_weave_retrieval_started` | `OnRetrievalStarted` |
| `weave.retrieval.completed` | `forge_weave_retrieval_completed` | `OnRetrievalCompleted` |
| `weave.retrieval.failed` | `forge_weave_retrieval_failed` | `OnRetrievalFailed` |
| `weave.document.deleted` | `forge_weave_document_deleted` | `OnDocumentDeleted` |
| `weave.reindex.started` | `forge_weave_reindex_started` | `OnReindexStarted` |
| `weave.reindex.completed` | `forge_weave_reindex_completed` | `OnReindexCompleted` |

`NewMetricsExtension()` writes to its own collector, so these counters don't show up in your app's metrics endpoint. In a Forge app, build it from the app's metrics:

```go
import (
    "github.com/xraph/weave/observability"
    gu "github.com/xraph/go-utils/metrics"
)

// With a Forge app's MetricFactory:
metricsExt := observability.NewMetricsExtensionWithFactory(fapp.Metrics())

// With a standalone collector (useful for testing):
metricsExt := observability.NewMetricsExtensionWithFactory(
    gu.NewMetricsCollector("my-service"),
)
```

Each counter is a public field, so you can read it directly:

```go
fmt.Println("ingests completed:", metricsExt.IngestCompleted.Value())
fmt.Println("chunks created:", metricsExt.ChunksCreated.Value())
```

## Logging

The engine takes a go-utils `log.Logger` (the same logger type Forge uses), not a `*slog.Logger`:

```go
import log "github.com/xraph/go-utils/log"

eng, err := engine.New(
    // ...
    engine.WithLogger(log.NewProductionLogger()),
)
```

Without `WithLogger` the engine logs nothing. The Forge extension passes the app's logger for you; an `engine.WithLogger` you pass with `extension.WithEngineOption` wins. The engine logs at warn level when:

- deleting a collection's or document's vectors fails (the metadata delete still goes ahead). The line has the collection or document ID and `error_type`.
- a lifecycle hook returns an error. The line has the hook, the plugin and `error_type`. One hook of one plugin logs at most once a minute, and `suppressed` says how many errors it stood for since its last line.

Neither line logs the error's text. A store error can quote a DSN or a host, and a hook's error can quote whatever the hook was handed.
