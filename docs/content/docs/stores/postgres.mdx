---
title: PostgreSQL Store
description: Production metadata store backed by PostgreSQL using Grove, plus the pgvector vector store.
---

The `store/postgres` package keeps collections, documents and chunks in PostgreSQL through [Grove](https://github.com/xraph/grove). The `vectorstore/pgvector` package keeps the embeddings in the same database. Both take a `*grove.DB`, so you open one connection and share it.

## Setup

```go
import (
    "github.com/xraph/grove"
    "github.com/xraph/grove/drivers/pgdriver"

    "github.com/xraph/weave/chunker"
    "github.com/xraph/weave/engine"
    "github.com/xraph/weave/store/postgres"
    "github.com/xraph/weave/vectorstore/pgvector"
)

pgdb := pgdriver.New()
if err := pgdb.Open(ctx, os.Getenv("DATABASE_URL")); err != nil {
    log.Fatal(err)
}
db, err := grove.Open(pgdb)
if err != nil {
    log.Fatal(err)
}

st := postgres.New(db)
if err := st.Migrate(ctx); err != nil {
    log.Fatal(err)
}

eng, err := engine.New(
    engine.WithStore(st),
    engine.WithVectorStore(pgvector.New(db)),
    engine.WithEmbedder(emb),
    engine.WithChunker(chunker.NewRecursiveChunker()),
)
```

Pool settings go on the driver's `Open`, with the options in `github.com/xraph/grove/driver`:

```go
pgdb := pgdriver.New()
if err := pgdb.Open(ctx, dsn, driver.WithPoolSize(25)); err != nil {
    log.Fatal(err)
}
```

## Migrations

`st.Migrate(ctx)` runs `postgres.Migrations`, a Grove migration group named `weave`, through Grove's orchestrator. Each version gets one row in `grove_migrations`, so a second call applies nothing.

Weave v1.8 and earlier ran every migration's `Up` on each start and recorded nothing. You don't need to do anything when you upgrade from one of those. Every migration is written with `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS`, so the first tracked run finds your tables already there, leaves the rows in them alone and records the versions.

The Forge extension calls `Migrate` on `Start` unless you set `disable_migrate`. Set it when your app runs its own Grove orchestrator, and add `postgres.Migrations` to that run.

## Schema

| Table | Holds |
|-------|-------|
| `weave_collections` | Collections. `UNIQUE (tenant_id, name)`. |
| `weave_documents` | Documents. `UNIQUE (collection_id, content_hash)`, and a foreign key to the collection with `ON DELETE CASCADE`. |
| `weave_chunks` | Chunk text, offsets and metadata, with foreign keys to the document and collection |

All three have a `tenant_id` column and an index on it. Only `weave_collections` has `app_id`. Metadata maps are stored as `JSONB`.

The unique constraints are where `weave.ErrCollectionAlreadyExists` and `weave.ErrDuplicateDocument` come from.

## Lifecycle

| Method | Behaviour |
|--------|-----------|
| `Migrate(ctx)` | Applies pending migrations through the orchestrator |
| `Ping(ctx)` | Pings the database |
| `Close()` | Closes the `*grove.DB` |

`engine.Stop` calls `Close`, so stopping the engine closes the database for everything else that shares it, pgvector included.

## pgvector

`vectorstore/pgvector` stores one row per chunk and searches with pgvector's cosine distance operator (`<=>`), returning `1 - distance` as the score.

Nothing in Weave creates its table or the extension. Create them yourself, in your own migrations, before the first ingest:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE IF NOT EXISTS weave_vectors (
    id        TEXT PRIMARY KEY,
    embedding vector(1536),
    content   TEXT,
    metadata  JSONB
);
```

The column names and types come from the store's queries: `id` is the chunk ID and the upsert conflict target, `embedding` is the vector, `content` is the chunk text and `metadata` holds `collection_id`, `document_id`, `tenant_id`, `chunk_index` and the chunk's own metadata, filtered with `metadata->>'key'`. The `1536` is the output size of `text-embedding-3-small`; use your embedder's `Dimensions()`.

Weave doesn't create a vector index either. For a large table, add one for cosine distance, for example `CREATE INDEX ON weave_vectors USING hnsw (embedding vector_cosine_ops);`.

```go
vs := pgvector.New(db)
```

`pgvector.WithTableName(name)` exists, but only `Search` reads the custom name. `Upsert`, `Delete` and `DeleteByMetadata` always write `weave_vectors`, so leave the table name at its default for now.

## Forge extension

With Weave as a Forge extension, the metadata store can come from a `*grove.DB` in the container: the extension sees the `pg` driver and builds `store/postgres` for you. The vector store doesn't, so pass pgvector yourself:

```go
weaveext.New(
    weaveext.WithGroveDatabase(""), // the default grove.DB
    weaveext.WithVectorStore(pgvector.New(db)),
    weaveext.WithEngineOption(engine.WithEmbedder(emb)),
    weaveext.WithEngineOption(engine.WithChunker(chunker.NewRecursiveChunker())),
)
```

See [Forge extension](/docs/guides/forge-extension#using-a-grove-database).
