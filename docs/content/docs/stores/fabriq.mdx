---
title: Fabriq Vector Store
description: Back weave's VectorStore with the fabriq data fabric, so chunk embeddings live in the same store as the rest of your system.
---

The `fabriqvec` adapter (`github.com/xraph/weave/vectorstore/fabriq`) implements `vectorstore.VectorStore` over [Fabriq](https://github.com/xraph/fabriq)'s vector plane. Instead of a separate `weave_vectors` table, Weave's chunk embeddings go into Fabriq's vector store, next to the rest of your data, where Fabriq's own recall can see them.

It only replaces the vector store. Weave keeps its loaders, chunkers, retrievers and metadata store.

```go
import (
    "github.com/xraph/weave/chunker"
    "github.com/xraph/weave/engine"
    fabriqvec "github.com/xraph/weave/vectorstore/fabriq"
)

eng, err := engine.New(
    engine.WithStore(metaStore),
    engine.WithVectorStore(fabriqvec.New(f.Vector())),
    engine.WithEmbedder(emb),
    engine.WithChunker(chunker.NewRecursiveChunker()),
)
```

`New` takes a Fabriq `query.VectorQuerier`, which a started Fabriq facade gives you through `f.Vector()`. All Weave vectors sit under one Fabriq entity, `weave_vector` unless you set another with `WithEntity`.

## Configuration

```go
fabriqvec.New(f.Vector(),
    fabriqvec.WithEntity("kb_chunks"), // the Fabriq entity these vectors live under
)
```

### Finding Fabriq in the container

In a Forge app with Fabriq in the DI container, `EngineOption` finds it by its `query.Fabric` port and sets the vector store. When Fabriq isn't there, it does nothing, so you can always include it:

```go
eng, err := engine.New(
    engine.WithStore(metaStore),
    fabriqvec.EngineOption(app.Container()),
    engine.WithEmbedder(emb),
    engine.WithChunker(chunker.NewRecursiveChunker()),
)
```

With the Weave Forge extension, pass it as `weaveext.WithEngineOption(fabriqvec.EngineOption(app.Container()))`. `EngineOption` looks Fabriq up when you call it, not when the engine is built, so call it after Fabriq is in the container. Otherwise you silently get no vector store.

## Behaviour

| `VectorStore` call | Fabriq |
|--------------------|--------|
| `Upsert(entries)` | One Fabriq `Upsert` per entry, under the Fabriq tenant the entry's `tenant_id` names. `Content` goes into the meta map under `content`, and `Metadata` sits alongside it. A batch with an entry lacking `metadata["tenant_id"]` is `ErrTenantRequired` and nothing is written. |
| `Search(vec, opts)` | Fabriq `Similar` with `opts.Filter` as the metadata filter. `opts.TenantKey` is required (`ErrTenantRequired` without it) and sets Fabriq's tenant scope on the context. `MinScore` filters afterwards. `Content` and `Metadata` are rebuilt from the meta map. |
| `Delete(ids)` | One Fabriq `Delete` per ID, under the context's weave tenant |
| `DeleteByMetadata(filter)` | Fabriq `DeleteByMeta` under the filter's `tenant_id`, all key/value pairs must match. An empty filter is `ErrInvalidArgument`, one without `tenant_id` is `ErrTenantRequired` |

Differences from the pgvector store:

- `Search` results have a nil `Vector`, because Fabriq's similarity search doesn't return embeddings. That breaks MMR's diversity term, so `NewMMRRetriever` over Fabriq ranks by relevance alone.
- The score is whatever Fabriq returns. Weave doesn't know which metric that is, and `eng.Components()` reports it as unverified.
- `TenantKey` becomes a Fabriq tenant scope. The engine's `tenant_id` metadata filter still applies on top of it, so both have to match.

## Requirements

- A started Fabriq facade with its vector storage migrated, using Fabriq's own migrations.
- Each upserted entry is written under the Fabriq tenant its `metadata["tenant_id"]` names, whatever Fabriq tenant is on the context. That tenant ID has to be one Fabriq accepts (letters, digits, `_` and `-`, up to 64), or the whole batch is refused. `DeleteByMetadata` runs under the Fabriq tenant its filter's `tenant_id` names, and a filter without one is `ErrTenantRequired`. `Delete` runs under the weave tenant on the context (`weave.WithTenant`), falling back to a Fabriq tenant already there, and is `ErrTenantRequired` with neither. The engine always sends both.

## Choosing a vector store

- `vectorstore/memory` for development and tests.
- `vectorstore/pgvector` for a standalone Postgres with pgvector, in a table Weave migrates.
- `vectorstore/fabriq` when you already run Fabriq and want chunk vectors in it.
